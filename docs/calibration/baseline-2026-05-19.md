## L1 baseline (classifier recall — interim proxy)

True L1 requires labeled fixtures (Phase 3 `annotate-segments` output). Until then, the only proxy is _internal consistency_ between the HSV-cosine `color_class` and the final `screen_type` from `frame_classifications` in `segments.json`. Match 463 (full 28-min capture, 1680 frames sampled at 1 fps):

| color_class               | frames | accepted by anchor gate |  "recall" |
| ------------------------- | -----: | ----------------------: | --------: |
| player_loadout_view       |  1,230 |                       2 |  **0.2%** |
| pre_game_lobby_state_2    |    226 |                      12 |      5.3% |
| post_game_events          |     88 |                       4 |      4.5% |
| post_game_player_summary  |     72 |                       1 |      1.4% |
| post_game_action_tracker  |     52 |                      49 | **94.2%** |
| post_game_net_chart       |      6 |                       0 |      0.0% |
| post_game_faceoff_map     |      5 |                       1 |     20.0% |
| post_game_box_score_goals |      1 |                       1 |    100.0% |

**Caveat:** the bulk of `color_class=player_loadout_view` predictions are mid-gameplay frames where the scoreboard overlay shares HSV signature with a loadout card. Those are _correctly rejected_ by the anchor-text gate, so the 0.2% number overstates the failure. Until labeled fixtures land we cannot distinguish "rejected scoreboard false positive" (good) from "rejected real loadout card" (bad).

The hard signal: on match 463, of the entire 28-minute capture, **only 2 frames were accepted as `player_loadout_view`** — both at video start showing HenryTheBobJr's card. The user confirms cycling through all 10 loadout cards happened in the recording. Therefore the anchor-text gate is dropping real loadout cards somewhere; we just can't quantify how many without ground truth.

## Remaining open items after Phase 5a + 5c

- **Class A (4)** — heavy OCR variants distance 2-3, opp-side only. Either widen Levenshtein floor to 2 selectively, OR accept as flagged-for-operator-review (current behavior).
- **Class C (6)** — chevron collision pairs in match_events. The matcher needs either clock-aware clustering or event-first matching.
- **L3 (#9 above)** — `match_shot_type_summaries` 6/8 gap.
- **Phase 0** — loadout attribute coverage. Blocked on Phase 3 (annotator) + Phase 5 classifier work.

## Open architectural questions for Phase 4 review

These are the design-level questions that need external input before Phase 5b.2 or Phase 0 work proceeds:

1. **Clock-aware vs spatial-only clustering.** The current matcher clusters chevrons in pixel/hockey space only. Should clock-distance be a secondary clustering dimension, or should we go to fully event-first matching (use `selected_event_index` per frame)?
2. **Anchor-text gate vs HSV-only acceptance for `player_loadout_view`.** Match 463 has 1,230 frames where color matches but anchor text fails. How aggressive should the gate be? Trade-off: looser = more false positives during gameplay scoreboard; tighter = miss real loadout cards.
3. **Single-prototype vs multi-prototype classifier per class.** Classifier is calibrated against ONE PNG per class today. The plan calls for averaging multiple fixtures into one centroid. Is averaged HSV histogram appropriate for visually-multimodal classes (10 different loadout cards with different player photos)?
4. **Operator labeling effort.** Phase 3 `annotate-segments` CLI puts ~5 min of labeling per match on the operator. Acceptable scaling? Or is there a path to fully auto-labeled fixture growth?

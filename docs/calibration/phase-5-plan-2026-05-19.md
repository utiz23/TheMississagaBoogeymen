## Pivotal question that decides everything else

> **Do the 6 Class C marker-collision pairs on match 463 produce user-visible errors on the rendered match page?**

If **YES** → cheap matcher patch (Step A below). Architectural rewrite deferred until ≥2-3 matches show recurring corruption.

If **NO** → matcher work is pixel-perfectionism. Skip Step A entirely. Class C stays as a _report flag for operator awareness only_.

This empirical check is the prerequisite for any Phase 5b.2 work. Until it's answered, every architectural recommendation is uncosted.

## Decisions per question

### Q1 — chevron matcher

**Choose:** Empirically gate on user-visible corruption (cheap probe), THEN decide.

**Justification:**

- External (load-bearing): "Six collision pairs on one match is not a season-wide problem… If those pairs do not materially distort the site's visible outputs, then a sophisticated matcher rewrite is pixel-perfectionism."
- Internal: Rec 1's Stage A is structurally broken — `selected_event_index` doesn't link to `match_event_id` in the DB. Implementing as-research-described needs a schema/storage hop the research didn't surface.
- Research's expected gain (91.8% → 95–97% L2) is conditional on the failure mode being meaningful. External challenges whether 91.8% → 95% on this metric matters at all.

**Action:**

1. Open the rendered match-463 page and inspect each of the 6 collision-pair events. Document whether the user can tell something is wrong.
2. If YES on any: apply the cheapest mitigation that clears the visible defect (likely null-out the lower-confidence position of the pair, leaving one event unpositioned). No new code.
3. If NO: Class C stays as a `match-quality` report warning. Phase 5b.2 deferred indefinitely.

### Q2 — anchor gate

**Choose:** Do nothing.

**Justification:**

- Internal: research misidentifies the root cause. The gate isn't a boolean substring; `fuzzy_contains` has implicit score via Levenshtein window. The real bottleneck is _OCR recall_ on transient frames where the anchor text simply isn't returned. A calibrator on top of `fuzzy_contains` cannot recover frames with no OCR output.
- External: even if a scored gate worked, it's over-engineering for 30 matches/season. Hand-tune + flag is a valid product decision.

**Action:** No code change. Document in HANDOFF.md as "deferred — root cause was misdiagnosed by research; revisit after more matches reveal whether `player_loadout_view` recall is a real product gap."

### Q3 — multi-prototype classifier

**Choose:** Defer until either Phase 3 labeling produces evidence the centroid is mis-classifying OR new matches surface variant cards that the single centroid misses.

**Justification:**

- Research: real concern (within-class multimodality is legitimate).
- Internal: K=1 reduces to current behavior; safe-to-implement.
- External: don't build classifier infrastructure before proving the classifier problem matters in production. We have 2 matches; need ~5+ with diverse opponents before multi-prototype is worth the calibration time.

**Action:** Add a TODO comment in `calibrate_classifier.py` next to the per-class centroid averaging loop noting that K>1 should be considered when fixture diversity grows. No code change yet.

### Q4 — labeling loop (annotate-segments CLI)

**Choose:** Build a **minimal v0** — 10-frame fixed cap per match, single ranker (disagreement only), no manifest/DVC overhead.

**Justification:**

- Research: active sampling is right in principle.
- Internal: 5-min budget needs an explicit top-N cap, otherwise it's aspirational.
- External: even 10-min is optimistic with selection overhead. Strip the task to ~15-20 clicks total.

**Action:**

- `tools/video_ingest/video_ingest/annotate.py` — single CLI, single ranker
- Sampling rule: top-10 frames where `screen_type=unknown_screen AND color_score > 0.7` (one criterion, easy to reason about)
- Output: PNG dropped into `tools/game_ocr/calibration/extras/<class>__match<id>_t<seconds>_<opp>.png` (existing naming convention)
- No labels manifest, no eval split, no per-class CI gates yet — those land only if the corpus actually grows past ~5 matches

This produces a usable tool in under a day. Defer the labels/eval/DVC infrastructure until corpus growth proves the need.
